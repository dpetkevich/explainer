How Lanyon AI Works

AI models can now write a full physics simulation in minutes. They can also slip in a sign error that runs stably, converges smoothly, and reports the wrong physics with total confidence. The standard fix: have the AI also write a proof that its code is correct. But that plan has a hole. The proof can be flawless while describing code you aren't actually running. Lanyon AI generates the code and the proof from one shared source, so the two can never disagree. That single architectural move turns 'probably correct' into 'correct by construction.'

The basic building blocks

Before any AI enters the picture, you need to see the problem domain: a physics simulation where a tiny code error doesn't crash anything — it quietly lies. We build one concrete simulation, break it invisibly, and then ask what 'correct' even means.

One equation governs the whole simulation: whatever flows in must be accounted for

Meet the Sod shock tube: a standard gas-dynamics benchmark — high-pressure gas on the left, low on the right, diaphragm removed at t=0. Every symbol in the governing law is labeled on the tube itself.

A subtly broken solver runs smoothly and reports wrong physics

The tube's continuous equation gets replaced by arithmetic on a grid of cells, with a flux formula moving mass between neighbors. Before you drag the slider: do you expect a mis-coded flux to crash the run, or just quietly lie?

An LLM writing 100,000 tokens almost never writes all of them right

You just saw that one wrong coefficient is enough — now watch an LLM write your solver token by token, each token a short text fragment sampled from a learned distribution, with nothing enforcing the math. Slide the per-token accuracy up and watch what happens over 100,000 tokens.

'Correct' only means something relative to a written specification

The broken solver of scene 2 wasn't 'incorrect' in a vacuum — it violated a nameable property. A specification writes that property down formally; verification means proving the code satisfies it.

The new technology

Scene 4 left us with a precise target — prove that code matches a written specification. Here we meet the machinery that checks such proofs, watch the obvious AI-based approach fail at exactly one seam, and see how Lanyon welds that seam shut.

Proofs are hard to write but mechanical to check

Scene 4 demanded a proof that the code satisfies the spec — but who checks a proof written by an untrustworthy author? A proof assistant: a small, audited program that accepts a proof only if every step follows mechanically from the rules, the way a compiler rejects a syntax error.

The consensus fix: have the LLM write both the code and its proof

Given a trustworthy checker, the obvious architecture writes itself: the LLM emits both the shock-tube solver and a machine-checkable proof, gated by scene 5's kernel. Step through the pipeline — an accepted proof means the code it describes provably satisfies the spec.

Lanyon shrinks the LLM's job to twenty lines of specification

If the LLM is the unreliable link, Lanyon gives it the smallest possible job: a ~20-line specification in a DSL, never code or proof. The DSL is a compact formal language with conservation laws and discretization schemes built in as vocabulary.

Code and proof are generated from one source, so they cannot disagree

Now the payoff: the symbolic engine expands that 20-line spec into the solver and its proof in one deterministic pass. There is no seam to tear because there was never a second artifact to drift — try to recreate scene 7's attack.

Why it beats existing tech

Correctness by construction isn't just safer than having a frontier model write everything — because the fallible, expensive component now touches only tens of lines, it is also dramatically faster and cheaper. The economics fall out of the architecture.

Twenty LLM lines expand into tens of thousands of verified lines

With the engine doing the writing, cost stops scaling with output size. Drag the output size up: the top-end model's line climbs with every token, while Lanyon's LLM cost stays flat at one 20-line spec.

Why now

One honest boundary remains on the guarantee, and it decides where this technology lands first: the industries where a silently wrong simulation costs the most.

The guarantee covers spec-to-code, not intent-to-spec

Scene 4 defined correctness relative to a spec — but who checks the spec against your intent? Nudge the spec away from your request and watch every seal stay green: Lanyon flawlessly, provably solves the wrong problem.

Verification, not generation, is now the bottleneck for critical code

Every system Lanyon targets — Euler gas dynamics, Maxwell's equations, magnetohydrodynamics for plasmas — is our shock tube's conservation law with more components, running inside rocket nozzles, satellite thrusters, and reactor designs.
