Physical Intelligence's MEM: Giving Robots a Memory

The AI that runs today's best robots sees only the current camera frame — nothing it did a second ago. So a robot that just dropped a bowl sees the same scene as one that never tried, and repeats the mistake forever. Why not feed in the whole video history? Because the computer work grows with the square of the video's length, and the robot has only a few hundred milliseconds to pick its next move. Physical Intelligence's MEM keeps two memories instead — compressed video for the last minute, plus a short text note the robot rewrites itself for everything older — and that lets one robot clean a kitchen for 15 minutes straight.

The basic building blocks

Before the fix, the problem. We follow one robot on one job — cleaning an entire kitchen, a 15-minute task — and see what the program controlling it actually is, what it computes each step, and why simply feeding it the past video runs past the robot's split-second time budget.

The robot's controller sees only the current frame — the past is invisible to it

Our running example: one robot cleaning a whole kitchen. Its policy — the function pi that picks the actions — reads only the current camera frame ot and the text goal g, then outputs joint commands for the next H steps (the action horizon it commits to). Step past the dropped bowl: frame 4 is identical to frame 1, so pi repeats the same doomed grasp.

One camera frame is cut into hundreds of pieces before the policy can use it

This policy is a vision-language-action model (VLA): an AI built on a network already trained on internet images and text, then taught to output robot actions. It cuts each 448×448 kitchen frame into small patches, and a vision transformer (ViT) turns each patch into a list of numbers called a token. Those tokens feed a Gemma3-4B language model and an 860M-parameter action network; drag across the four cameras to tally thousands of tokens per single timestep.

Feeding in past frames blows the robot's split-second time budget almost at once

These models work by comparing every token with every other token — the step called attention — so its cost grows with the square of the number of tokens. Append T past frames and the work grows about T2-fold: drag T and watch the compute curve cross the red deadline. Fifteen minutes of history sits orders of magnitude past the few-hundred-millisecond budget, even on an H100 GPU.

The new technology

The naive approach fails because it treats all memory alike. MEM's move: notice that seconds-old memory and minutes-old memory need wildly different amounts of detail, and store each in its own form — recent video, distant text.

Seconds-old memory needs pixels; minutes-old memory needs a sentence

That wall stands only if all memory must be raw video — slide back through the kitchen robot's last 15 minutes to see why it doesn't have to be. Retrying the slipped bowl grasp from 3 seconds ago needs pixel-level detail like grasp angle and bowl height, while 'I already put the butter away' from 9 minutes ago is a few bits that fit in one sentence.

MEM splits the policy in two, with a text memory as the only channel to the deep past

MEM breaks the single policy into two. A high-level policy reads the current frame and the text note m, then hands the low-level policy a one-line subtask l ('pick up the bowl') and rewrites the note to mt+1; the low-level policy sees only the last K frames plus that subtask and outputs the motor commands. In symbols (tap any symbol for its job): piapproxpiLL(at:t+Hmidot-K:t,lt+1,g);piHL(lt+1,mt+1midot,mt,g). The key fact: anything older than the last K frames survives only if it was written into the note m.

The model rewrites its own summary, so minute-scale memory costs almost nothing

Press play on the 15-minute kitchen episode and watch m get rewritten: 'a light green bowl, a dark blue bowl and a bright yellow bowl' compresses into 'three bowls in the top right cabinet', while stale facts get deleted outright. The token counter stays flat at a few dozen for the whole 15 minutes.

Attending across space and time separately makes video memory nearly as cheap as one image

To keep real pixels from the last K = 18 frames — about a minute — comparing every patch with every other across all frames would cost O(n2K2), with n patches per frame. MEM instead compares patches only two cheap ways: within a frame (space), and — in every 4th ViT layer — each patch only with itself across frames (time). Cost drops to O(Kn2+nK2), and the top layers throw away every past-frame patch, so the language model still sees just one frame's worth of tokens.

The video encoder adds no new weights, so its internet-trained vision carries over untouched

Feed the video encoder a single image and it computes exactly what the original image network did — so all its internet-trained vision knowledge carries over untouched. The trick: the only additions are the new across-time comparison pattern and a fixed (non-learned) clock signal e(t) built so e(0)=0. Slide K down to 1 and that clock adds nothing, so the output matches the original ViT exactly — zero new parameters, zero change on single images, so the encoder bolts onto any existing VLA.

Why it beats existing tech

Two memories are now in place: 18 frames of compressed video and one rewritten sentence. Here we run them head-to-head against the no-memory robot and the obvious shortcuts, on the paper's own experiments.

Logging every failed try makes the robot's history unlike anything it trained on

The obvious cheap shortcut logs every past subtask, so when the robot's grasp slips twice the log reads 'pick up bowl, pick up bowl, pick up bowl'. The robot trained on tidy human demonstrations where each step is said once, so this repetition is input it never saw in training — and models act unreliably on inputs unlike their training data. MEM's summary simply doesn't update until the bowl is in hand, so its input still looks like training.

Short-term visual memory lets the robot stop repeating the same failed grasp

Toggle memory over identical failure data. π0.6 — the no-memory robot MEM builds on — keeps trying the same doomed grasp forever, because its input never changes. MEM sees the failed attempt inside its 18-frame window and changes tactics on the next try: a different grasp height for the low chopsticks, or the opposite pull on an ambiguous fridge door (Fig. 5).

Every one-kind-of-memory design fails some task; only mixing video and text covers all four

On the paper's four memory tests (Fig. 6): Pool-Memory averages all past frames into a single token and blurs away which of three mugs went where. Proprio-Memory keeps only the robot's own joint angles, so it counts its coffee scoops fine but guesses among four drawers at the 25% chance floor. Memoryless π0.6 sits at chance everywhere. Only MEM clears all four, because each kind of memory demand reaches a form that keeps the right details.

Why now

Adding memory to robots has been tried before, and it often made them worse. The last piece is why MEM works where those tries failed — and the answer is the training data, not the wiring.

Memory only helps if it's trained on diverse data from the start — which is why earlier tries failed

Toggle the recipe (Fig. 7). Add the video memory only at the end, tuning on one task's tidy demos, and the robot barely uses its history: it takes a shortcut, copying its own last action instead of reading the scene. MEM instead trains the memory from the start on a broad mix — robot demos, its own trial runs, human corrections, and internet video — which kills that shortcut. Starting at 6 frames (1-second spacing) and stretched to 18 frames (54 s) later, it matches the best no-memory robots on shirt folding and box building instead of getting worse.
